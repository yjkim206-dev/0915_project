# 서비스 백업

관리자 → 환경설정 → 서비스 백업에서 자동 실행, 일별·주별·월별·분기별·년별 주기, 한국 시간 실행 시각, 보관 기간을 설정합니다. 기본값은 매일 오전 3시, 3년입니다. 주별은 요일을 선택하고 월별은 매월 1일, 분기별은 1·4·7·10월 1일, 년별은 1월 1일에 시작합니다. 예약 작업은 매분 확인합니다. 사용 중인 작업이 있으면 중복 실행하지 않습니다. 보관 기간 변경은 새 백업부터 적용합니다.

## 저장 범위와 구조

- `service-backups` 비공개 버킷의 `YYYY-MM-DD/실행 UUID/` 아래 저장합니다.
- `database/스키마.테이블/페이지.json.pgp`: public 서비스 테이블(게시글, 댓글, 회원, 결제, 구독, 크레딧, 설정 등), Auth users·identities·mfa_factors, Storage 버킷 설정, DB 마이그레이션 이력을 100행 단위로 저장합니다. 실행 이력과 백업 작업용 테이블은 중복 백업하지 않습니다.
- DB 데이터는 PostgreSQL의 동일 MVCC 조회 스냅샷에서 추출하며 OpenPGP AES-256으로 암호화한 후 Storage에 올립니다. 계정 비밀번호 해시와 결제 관련 민감한 서버 데이터도 평문으로 저장하지 않습니다. DB 파일의 SHA-256은 manifest에 기록합니다.
- `files/원본버킷/원본경로`: 백업 버킷을 제외한 Storage의 실제 파일을 복사합니다. 원본의 버전이 도중에 바뀌거나 사라지면 실패 처리하며 부분 백업을 완료로 표시하지 않습니다. 파일은 비공개 버킷의 Storage 접근 제어로 보호됩니다. DB와 별도로 파일을 복사하므로 복사 중 변경 없는 원본 버전이 필요합니다.
- `manifest.json`: DB 스냅샷 시각, 파일 경로·버전·크기, DB 파일 해시, 만료일 및 제외 범위입니다.
- 소스코드·프론트·Edge Function·스키마 정의는 GitHub의 해당 버전을 사용합니다. 호스팅 환경 변수·관리 토큰·일시적인 Auth 세션·로그인 토큰은 백업하지 않습니다. 외부 Toss 거래 및 카카오 계정 자체도 이 백업으로 복원되는 대상이 아닙니다.

이 기능은 서비스 데이터의 논리 백업입니다. Supabase 인프라 전체의 물리 백업/PITR을 대신하지 않습니다. Supabase 기본 DB 백업에도 실제 Storage 파일은 포함되지 않으므로 파일 복사를 함께 처리합니다.

## 보관 및 다운로드

관리자만 실행·설정·이력·다운로드 API에 접근할 수 있습니다. 버킷은 공개하지 않으며 일반 회원에게 읽기 정책을 만들지 않습니다. 다운로드 링크는 60초간 유효합니다. 백업 이력은 50건씩 페이지로 조회하며 이전 백업도 해당 보관 기간까지 다운로드할 수 있습니다.

백업이 만료되면 파일을 100개씩 정리한 뒤 삭제 완료로 기록합니다. 완료된 DB의 암호화 임시 데이터는 DB에서 비웁니다. 진행 중에는 임시 데이터가 있으므로 DB 여유 공간도 필요합니다. 백업 실패는 관리자 이력에서 확인하고 수동으로 새 실행을 요청합니다. 중단된 작업은 임대 시간이 끝나면 이어서 처리합니다.

**3년간 매일 전체 파일을 복사하면 원본 파일 용량의 약 1,095배까지 누적될 수 있습니다.** 관리자에 실제 백업 Storage 사용량을 표시합니다. Supabase 요금제의 용량·요금 한도는 별도 적용됩니다. 같은 프로젝트의 백업은 프로젝트 삭제·계정 접근 상실을 견디지 못하므로 외부 사본도 보관하세요.

## 암호화 키와 복구

`backend/supabase/configure-backups.mjs`는 최초에 48바이트 임의 키를 생성해 무시된 루트 `.env`의 `BACKUP_ENCRYPTION_KEY`와 Supabase Edge secret에 저장합니다. 프론트·GitHub·백업 버킷에 넣지 않습니다. **키는 별도로 안전하게 보관해야 합니다. 키를 교체하면 이전 백업에는 이전 키가 필요합니다.** 키와 복호화된 DB에는 계정/결제 민감 정보가 있으므로 공개하지 마세요.

복구는 먼저 격리된 Supabase 프로젝트에서 수행합니다.

1. 완료된 실행의 manifest 및 모든 DB/Storage 파일을 다운로드합니다. DB 파일 해시를 manifest와 비교합니다.
2. 해당 GitHub 버전의 마이그레이션을 적용해 서비스 스키마·함수·RLS를 재구성합니다. Auth와 Storage는 호환되는 Supabase 버전을 사용합니다.
3. OpenPGP 호환 도구 또는 PostgreSQL `pgp_sym_decrypt`로 DB 파일을 복호화합니다. 각 파일은 `{table, rows}` JSON입니다. 키를 명령 인수나 로그에 노출하지 않습니다. 암호화 키 외에 기존 Auth/MFA 관련 서버 설정이 필요할 수 있습니다.
4. Auth users/identities, profiles, 서비스 테이블의 외래 키 의존 순서로 행을 복원하고 identity/sequence 값을 조정합니다. 결제 복구 시 외부 결제사의 실제 승인·환불 내역과 대조합니다.
5. 버킷 설정을 복원하고 manifest의 source_bucket/source_path에 Storage API로 파일을 업로드합니다. `storage.objects` 메타데이터를 SQL로 삽입하는 방식은 사용하지 않습니다.
6. 계정 로그인, 권한, 게시글 첨부, 결제/구독/크레딧 내역을 별도 검증한 후 운영 전환을 결정합니다. 운영 데이터 덮어쓰기나 자동 환불·결제 재실행은 이 기능에 포함하지 않습니다.

## 배포

`node backend/supabase/configure-backups.mjs`로 DB 024, 버킷, 키를 준비하고 API Edge Function과 프론트를 배포합니다. 기존 Vault의 `moa_subscription_cron_secret`을 재사용하며, cron은 private 내부 API에만 전달합니다. 암호화 키와 cron secret을 브라우저에 노출하지 않습니다.
