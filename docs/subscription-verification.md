# 이용권·자동갱신 구독 구현 및 검증 (2026-10-19)

## 결제창 구성

상점 기본 선택은 **1개월 이용권**이다. 크레딧과 같은 Toss
`requestPayment({ method: 'CARD', ... })` 일반 결제창을 사용하고 승인 후 한 달만
이용한다. 자동 청구는 하지 않는다. **자동갱신 구독**을 명시적으로 선택하면
`requestBillingAuth` 카드등록창을 사용하고 등록된 빌링키로 첫 달과 이후 만료 시 결제한다.
이는 [Toss 자동결제 연동 방식](https://docs.tosspayments.com/guides/v2/billing/integration)에 따른 차이다.

구독 상태·방식·이용기간·최근 결제·처리 이력은 유저 프로필과 관리자 회원정보에 표시된다.
자동갱신 해지 예약과 철회는 이미 결제한 기간을 유지한다. 현재 구독의 최근 결제를
전액 환불하면 이용이 종료된다. 과거 결제는 자동 환불 대상에서 제외해 별도 검토한다.

## 실제 적용

- 운영 프론트: `https://0915-project-ruby.vercel.app`
- Supabase: `ymprvqsfpwvoutwozwvn`, `api` Edge Function
- 마이그레이션: `019_subscription_lifecycle`, `020_subscription_schedule`, `021_subscription_failure_consistency`
- 예약 작업: `moa-subscription-renewals`, `*/5 * * * *`, 활성화 확인
- 전용 시크릿: 프로젝트의 비공개 `.env`, Supabase Edge secrets, Vault에 연결. 값은 저장소에 포함하지 않음
- 예약 API 전용 인증 실행: HTTP 200, 당시 갱신 대상 0건·만료 처리 0건
- 예약 API 공개 호출: HTTP 401

월간 청구 시기에만 갱신 대상이 된다. 주문별 고정 식별자, 결제 처리 임대와 토스
멱등키를 사용한다. 불명확한 승인 결과는 대기 상태로 보존하고 결제 상태 확인으로
조회한다. 승인 확인 전 이용권을 지급하지 않는다. 카드 거절은 주문 실패·구독
`past_due`·처리 이벤트를 원자적으로 기록하며 자동으로 반복 청구하지 않는다.

## 검증 결과

1. 코드 테스트 **31건 통과**: 기존 API/크레딧 21건과 구독 10건.
2. 실제 Supabase 구독 검증 **12개 시나리오 통과**:
   - 두 구매 방식과 가격, 대기 주문 재사용
   - 금액·결제 방식 검증, 처리 중 중복 청구·취소 차단
   - 검증된 결제만 한 달 이용권 활성화, 중복 지급 차단
   - 프로필·관리자 구독 화면·회원 목록의 상태 일치
   - 일반 유저 관리자 API·공개 예약 API 차단
   - 직접 Data API에서 빌링키와 내부 결제 처리 테이블 접근 차단
   - 환불 승인 전 이용 유지, 환불 완료 후 종료·중복 처리 차단
   - 해지 예약·철회와 관리자 처리자 기록
   - 해지된 구독의 만료와 추가 갱신 차단
   - 갱신 주문 중복 방지와 결제 거절 상태의 원자적 기록
   - 자동갱신 실패 후 일반 이용권으로 복구
   - 구독 처리와 크레딧 지갑의 독립성
3. 기존 크레딧 실제 DB 회귀 검증 **16개 시나리오 통과**, 테스트 데이터 삭제 확인.
4. 운영 Edge 브라우저 검증 **7개 그룹 통과**:
   - 이용권·크레딧은 일반 결제 SDK, 자동갱신은 명시적 카드등록 SDK 사용
   - 실제 토스 이용권 결제창의 카드 선택 화면 표시
   - 실제 토스 크레딧 결제창의 카드 선택 화면 표시
   - 실제 토스 자동갱신 카드등록 화면 표시
   - 유저 이용권 표시 및 환불 버튼과 DB 이용 종료 연동
   - 유저 자동갱신 해지·철회 버튼과 실제 DB 연동
   - 모바일 관리자 구독 조회·해지·환불 버튼과 유저 상태 일치
5. 프론트 빌드 및 코드 검사 오류 없음. 기존 Hook/미사용 코드 경고는 남아 있음.

실제 토스 창은 카드 선택/등록 항목이 보일 때까지 확인했지만 카드정보 제출과
토스 승인·취소는 실행하지 않았다. 활성화·환불은 명시적인 테스트 승인 결과와
실제 Supabase DB를 사용했으며, 브라우저 환불 검증에서도 결제 업체 응답만
모의 처리했다. 다음 달의 실제 자동 청구 완료를 증명하는 검증은 아니다.
검증에 사용한 임시 계정과 관련 DB 데이터는 삭제했다.
